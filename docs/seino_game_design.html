1. コンセプト

レストランで料理が来るまでの数分〜十数分を、子供が文字なし・音なしでも遊べる短時間対戦ゲームで潰す。 プレイヤー（タップ入力）とAIが交互に「合計を予想」しあう、簡易版モラ（Morra）ゲーム。 1ラウンドが数秒で終わるテンポ設計で、待ち時間の長さに合わせて何度でも気軽にリトライできることを重視する。

項目内容
技術スタックReact Native Web（同一コードでWeb配布。将来的なネイティブアプリ化の余地も残す）
配布形態Webアプリ（URLを開くだけで遊べる。App Store配信・審査対応は不要）
対応環境iPhone Safariのみを動作保証対象とする（自分のスマホで使う前提）
画面の向き縦・横両対応
通信要件毎回通信必須（オフラインPWA化はMVPでは見送り）
対象年齢層小学校低学年中心（6〜9歳）。現行のテンポ・タップサイズは実地検証済みでこのまま採用

2. 基本ルール

項目内容

出す本数0・1・2本の3択（ただし残り腕の本数が上限。詳細下記）

入力タイムアウト時の挙動制限時間内にタップがなければ自動的に「0本」を出したものとして扱う

1ラウンドの流れ

  • コール担当（ローテーションで自動決定）が予想数字を決める。選べる数字はその時点で両者が出せる最大本数の合計まで（下記参照）。自分の番のときだけ0〜4のボタンをタップして能動的に選択・画面表示する。AIの番のときはコール数字を一切表示せず、そのままカウントダウンへ進む（結果表示のタイミングで初めて公開）
  • 「3・2・1・せーの！」のカウントダウン演出（音声なし・視覚のみでも成立）
  • 制限時間内にプレイヤーが本数をタップ。自分の残り腕が1本の場合は「2」の選択肢が無効化される。AIも同様の制約下で本数を決定（詳細は3章）
  • 合計を即計算 → コール数字と一致していればコール担当の腕を1本下げる演出
  • 自動的に次ラウンドへ、コール担当を交代

合計の出現確率（腕の残り本数に応じて3パターン）

両者が出せる範囲内で均等ランダムに出したと仮定した理論値。腕が減るほど山が低い位置に寄っていく。

両者の腕出せる本数合計0合計1合計2合計3合計4
2本 vs 2本（通常）0-2 vs 0-2約11%約22%約33%約22%約11%
1本 vs 2本0-1 vs 0-2約17%約33%約33%約17%－
1本 vs 1本0-1 vs 0-1約25%約50%約25%－－

どちらかが1勝すると相手との合計レンジが狭まり、コールの選択肢も自動的に減る。先行した側ほど終盤に出せる本数が絞られるため、逃げ切りにくくキャッチアップが効きやすいバランスになる。

3. AIの駆け引きロジック

完全ランダムだと数ラウンドで「読めないだけの運ゲー」になってしまうため、直近のプレイヤーの傾向を追跡し、 コール時・防御時で異なる戦略を取らせる。プレイヤーが慣れてAIの癖を読み始めると、AI側の予測が外れ始める → プレイヤーがまた傾向を変える、という自然な読み合いのループを狙う。

公正性の原則（重要な前提）
攻撃側・防御側どちらの立場でも、判断材料は「相手の過去の履歴（統計）」のみであり、その回に相手が実際に何本出すかは、両者とも「せーの」で同時公開されるまで一切分からない。 AIはプレイヤーの実際の入力を覗き見ないし、プレイヤーもAIの実際の本数（内部的に決定済みでも）を事前に見ることはない。 これは実装上絶対に守るべき制約で、UI側でも「せーの」の前にAIの実際の手や結果を先出ししてはいけない。

3-1. 前提データ

humanHistory：直近8ラウンドでプレイヤーが出した本数（0/1/2）の記録

freq[n]：履歴内での本数 n（0,1,2）の出現割合。データが少ないうちは均等（1/3ずつ）扱い

maxSelf / maxHuman：AI自身／プレイヤーそれぞれの残り腕本数（＝その回に出せる最大本数、0〜2）

腕の本数制限を追加したため、以下のロジックは常に maxSelf と maxHuman の範囲内でのみ本数・コールを決定する（範囲外の値は候補に含めない）。

データのライフサイクル：humanHistory は連勝カウントと同様に「アプリセッション単位」で保持し、試合が変わっても明示的にはリセットしない（7章参照）。ページを閉じる／再読み込みするとクリアされる。

3-2. AIがコール担当のとき（攻撃側）

設計メモ：4章の変更で、AIのコール数字は「せーの」前には表示されず、結果画面で初めて公開する方式になった。 これにより、コール表示からplannedThrowを逆算されるリスクはそもそも発生しなくなった（表示自体がないため）。 ただし下記の「70%/30%」の仕組みはセキュリティ目的ではなく、AIも自分の計画通りにいかないことがある、という人間らしい不確実性の演出として、そのまま残す方針。 防御側（3-3）と同じ「戦略適用率」パラメータを使い回せる利点もある。 

1. freq を 0〜maxHuman の範囲だけに絞り、その中で最も出現率が高い本数を predictedHuman とする
2. AIの「投げるつもりの本数」plannedThrow を、0〜maxSelf の範囲でランダムに仮決定（Hard難易度では意図的に偏らせる）
3. コール = plannedThrow + predictedHuman（結果は自動的に 0〜(maxSelf+maxHuman) の範囲に収まる）
4. せーのの瞬間、AIの実際の本数は：
     Normal難易度：70%の確率で plannedThrow をそのまま出す（コール的中を狙う）
     残り30%は 0〜maxSelf の範囲で改めてランダムに出し直す（＝自分のコールを外すこともある）

つまりAIは「相手が一番出しがちな本数」に賭けてコールするが、必ずしも計画通りには出さない。コールはUI上せーの前には表示されないため逆算リスクはそもそも無いが、この70%/30%の仕組みは「AIも計画通りにいかないことがある」という人間らしい不確実性の演出として維持している。

3-3. プレイヤーがコール担当のとき（AIは防御側）

1. プレイヤーが宣言したコール数字 call は既に画面表示済み（選択肢自体が 0〜(maxHuman+maxSelf) に制限されている）
2. AIは x ∈ {0..maxSelf} のうち、freq[call - x] が最小になる x を選ぶ
   （call - x が 0〜maxHuman の範囲外なら確率0として扱う＝そもそも成立しない組み合わせ）
3. ただし常に最適解だと機械的すぎるので、
   Normal難易度では 70%の確率でこのロジックを適用、残り30%は maxSelf 範囲内でのランダム

AIは「プレイヤーが当てにきそうな手」を読んで、あえて外れる本数を選ぶ守備行動を取る。腕が減るほど選べる本数の幅も狭まるため、終盤ほど読み合いがシビアになる。

3-4. 難易度パラメータ

難易度履歴の参照数戦略適用率体感MVP実装
Easy参照なし0%（常にランダム）完全な運ゲー、小さい子向け見送り
Normal直近8ラウンド70%たまに読まれる／外される絶妙なバランスMVPで実装
Hard直近4ラウンド95%直近の癖に敏感、パターン化すると即対応される見送り

「戦略適用率」は攻撃側（3-2）・防御側（3-3）の両方に共通のパラメータとして使う。MVPでは難易度選択UIを作らず、Normal相当の駆け引きロジックを固定実装。Easy/Hardおよび自動調整ロジックはMVP検証後の拡張候補。

4-6. 中断時の挙動

6. AWSインフラ構成

バックエンド不要（認証なし・DB無し・AIロジックは全てクライアントサイドJS）のため、S3 + CloudFrontによる静的サイトホスティング構成とする。

[ブラウザ (iPhone Safari)]
        │ HTTPS
        ▼
   CloudFront（CDN配信、HTTPS終端、キャッシュ）
        │ OAC (Origin Access Control)
        ▼
   S3（静的ファイル配置、パブリックアクセス完全ブロック）

CI/CD:
GitHub Actions → OIDC federation → IAM Role（長期アクセスキーなし）
   → S3への同期 + CloudFrontキャッシュ無効化
項目内容
ホスティングS3（静的ファイル配置、ブロックパブリックアクセスON） + CloudFront（CDN配信、HTTPS終端）
S3アクセス制御CloudFrontからのみOAC（Origin Access Control）経由でアクセス許可。S3への直接アクセスは不可
独自ドメイン使わない。CloudFrontのデフォルトドメイン（*.cloudfront.net）で運用する（Route53・ACMは不要）
CI/CDGitHub Actions → OIDC federationでIAM Roleを引き受け（長期アクセスキーは持たない） → S3への同期 + CloudFrontキャッシュ無効化
想定コスト独自ドメインなしのため実質$0/月（S3ストレージ・リクエストはごく僅か、CloudFrontはデータ転送1TB/月・リクエスト1,000万件/月の無料枠内に収まる想定）
