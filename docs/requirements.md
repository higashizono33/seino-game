# せーの！ - 要件定義（v1.10時点のセッションサマリー）

レストランの待ち時間に子供が遊べる、AI対戦の親指本数当てゲーム。React Native Webプロジェクト `seino-game` の要件定義のインプットとして、これまでのセッションで決めた内容をまとめたもの。

## 1. コンセプト

レストランで料理が来るまでの数分〜十数分を、子供が文字なし・音なしでも遊べる短時間対戦ゲームで潰す。プレイヤー（タップ入力）とAIが交互に「合計を予想」しあう、簡易版モラ（Morra）ゲーム。1ラウンドが数秒で終わるテンポ設計で、待ち時間の長さに合わせて何度でも気軽にリトライできることを重視する。

## 3. 基本ルール

| 項目 | 内容 |
|---|---|
| 対戦形式 | プレイヤー（タップ操作） vs AI |
| 勝敗条件 | 各プレイヤーの腕は2本。先に両腕を下げた方（＝コール的中2回）が勝ち |
| 出す本数 | 0・1・2本の3択（ただし**残り腕の本数が上限**） |
| 本数選択の上限 | その回に出せる最大本数＝**そのプレイヤーの残り腕本数**（腕2本→0/1/2が選べる、腕1本→0/1しか選べない） |
| 合計の範囲 | 0〜4（両者とも腕2本のとき）。どちらかの腕が1本になると達成可能な合計の上限も自動的に下がる |
| コール担当 | 完全ローテーション（自分→AI→自分→AI…毎ラウンド交代） |
| 的中判定 | コール数字＝実際の合計 の場合、コール担当が自分の腕を1本下げる |
| 入力方式 | 「せーの！」の合図後、制限時間内（約0.9秒）に0/1/2をタップ。タップ即・結果表示 |
| 入力タイムアウト時の挙動 | 制限時間内にタップがなければ**自動的に「0本」を出したものとして扱う** |
| 試合間のルール | 1試合内はコール完全ローテーション。試合が決着したら、**勝者が次の試合の先行（最初のコール担当）**になる |
| AIコールの事前表示 | **表示しない**。AIがオフェンスのときはコール表示画面を出さず、いきなりカウントダウンへ進む。コール内容は結果表示画面で初めて公開する |

### 1ラウンドの流れ

1. コール担当（ローテーションで自動決定）が予想数字を決める。選べる数字はその時点で両者が出せる最大本数の合計まで。**自分の番のときだけ**0〜4のボタンをタップして能動的に選択・画面表示する。**AIの番のときはコール数字を一切表示せず**、そのままカウントダウンへ進む（結果表示のタイミングで初めて公開）
2. 「3・2・1・せーの！」のカウントダウン演出（音声なし・視覚のみでも成立するデザインにする）
3. 制限時間内にプレイヤーが本数をタップ。自分の残り腕が1本の場合は「2」の選択肢が無効化される。AIも同様の制約下で本数を決定（詳細は4章）
4. 合計を即計算 → コール数字と一致していればコール担当の腕を1本下げる演出
5. 自動的に次ラウンドへ、コール担当を交代

### 合計の出現確率（腕の残り本数に応じて3パターン）

両者が出せる範囲内で均等ランダムに出したと仮定した理論値。腕が減るほど山が低い位置に寄っていく。

| 両者の腕 | 出せる本数 | 合計0 | 合計1 | 合計2 | 合計3 | 合計4 |
|---|---|---|---|---|---|---|
| 2本 vs 2本（通常） | 0-2 vs 0-2 | 約11% | 約22% | 約33% | 約22% | 約11% |
| 1本 vs 2本 | 0-1 vs 0-2 | 約17% | 約33% | 約33% | 約17% | － |
| 1本 vs 1本 | 0-1 vs 0-1 | 約25% | 約50% | 約25% | － | － |

どちらかが1勝すると相手との合計レンジが狭まり、コールの選択肢も自動的に減る。先行した側ほど終盤に出せる本数が絞られるため、逃げ切りにくくキャッチアップが効きやすいバランスになる。

## 4. AIの駆け引きロジック

完全ランダムだと数ラウンドで「読めないだけの運ゲー」になってしまうため、直近のプレイヤーの傾向を追跡し、コール時・防御時で異なる戦略を取らせる。プレイヤーが慣れてAIの癖を読み始めると、AI側の予測が外れ始める → プレイヤーがまた傾向を変える、という自然な読み合いのループを狙う。

### 公正性の原則（重要な前提・実装で必ず守ること）

攻撃側・防御側どちらの立場でも、判断材料は「相手の過去の履歴（統計）」のみであり、**その回に相手が実際に何本出すかは、両者とも「せーの」で同時公開されるまで一切分からない**。AIはプレイヤーの実際の入力を覗き見ないし、プレイヤーもAIの実際の本数（内部的に決定済みでも）を事前に見ることはない。UI側でも「せーの」の前にAIの実際の手や結果、コール数字を先出ししてはいけない。

### 4-1. 前提データ

- `humanHistory`：直近8ラウンドでプレイヤーが出した本数（0/1/2）の記録
- `freq[n]`：履歴内での本数 n（0,1,2）の出現割合。データが少ないうちは均等（1/3ずつ）扱い
- `maxSelf` / `maxHuman`：AI自身／プレイヤーそれぞれの残り腕本数（＝その回に出せる最大本数、0〜2）

腕の本数制限があるため、以下のロジックは常に `maxSelf` と `maxHuman` の範囲内でのみ本数・コールを決定する（範囲外の値は候補に含めない）。

**データのライフサイクル**：`humanHistory` は連勝カウントと同様に「アプリセッション単位」で保持し、試合が変わっても明示的にはリセットしない（7章参照）。ページを閉じる／再読み込みするとクリアされる。

### 4-2. AIがコール担当のとき（攻撃側）

```
1. freq を 0〜maxHuman の範囲だけに絞り、その中で最も出現率が高い本数を predictedHuman とする
2. AIの「投げるつもりの本数」plannedThrow を、0〜maxSelf の範囲でランダムに仮決定（Hard難易度では意図的に偏らせる）
3. コール = plannedThrow + predictedHuman（結果は自動的に 0〜(maxSelf+maxHuman) の範囲に収まる）
4. せーのの瞬間、AIの実際の本数は：
     Normal難易度：70%の確率で plannedThrow をそのまま出す（コール的中を狙う）
     残り30%は 0〜maxSelf の範囲で改めてランダムに出し直す（＝自分のコールを外すこともある）
```

つまりAIは「相手が一番出しがちな本数」に賭けてコールするが、必ずしも計画通りには出さない。コールはUI上せーの前には表示されないため逆算リスクはそもそも無いが、この70%/30%の仕組みは「AIも計画通りにいかないことがある」という人間らしい不確実性の演出として維持している（防御側と同じ「戦略適用率」パラメータを使い回せる利点もある）。

### 4-3. プレイヤーがコール担当のとき（AIは防御側）

```
1. プレイヤーが宣言したコール数字 call は既に画面表示済み（選択肢自体が 0〜(maxHuman+maxSelf) に制限されている）
2. AIは x ∈ {0..maxSelf} のうち、freq[call - x] が最小になる x を選ぶ
   （call - x が 0〜maxHuman の範囲外なら確率0として扱う＝そもそも成立しない組み合わせ）
3. ただし常に最適解だと機械的すぎるので、
   Normal難易度では 70%の確率でこのロジックを適用、残り30%は maxSelf 範囲内でのランダム
```

AIは「プレイヤーが当てにきそうな手」を読んで、あえて外れる本数を選ぶ守備行動を取る。腕が減るほど選べる本数の幅も狭まるため、終盤ほど読み合いがシビアになる。

### 4-4. 難易度パラメータ

| 難易度 | 履歴の参照数 | 戦略適用率 | 体感 | MVP実装 |
|---|---|---|---|---|
| Easy | 参照なし | 0%（常にランダム） | 完全な運ゲー、小さい子向け | 見送り |
| Normal | 直近8ラウンド | 70% | たまに読まれる／外される絶妙なバランス | **MVPで実装** |
| Hard | 直近4ラウンド | 95% | 直近の癖に敏感、パターン化すると即対応される | 見送り |

「戦略適用率」は攻撃側・防御側の両方に共通のパラメータとして使う。MVPでは難易度選択UIを作らず、Normal相当の駆け引きロジックを固定実装。Easy/Hardおよび自動調整ロジックはMVP検証後の拡張候補。

## 5. 画面フロー仕様

同じ画面種別（せーの・タップ入力・結果表示）でも、コール担当がAIか人間かで文言や表示内容が変わる。以下、ロール別に一連の流れを記載。

### 5-1. 試合の入り口

**① タイトル画面**：ゲームタイトル「せーの！」、手のイラスト、「はじめる」ボタン。タップ後、1試合目のコール担当を決定（2試合目以降は前の試合の勝者が先行）。ここから毎ラウンド、5-2または5-3のどちらかの流れに分岐する。

### 5-2. AIがオフェンス（＝人間はディフェンス）の回

コール選択・表示画面は無し。いきなりカウントダウンから始まる。

1. **せーのカウントダウン**：topbarに両者の残り腕、本文に「3・2・1・せーの！」。AIのコール内容は非公開のまま進む。
2. **タップ入力（あなたの防御）**：残り時間バー、0/1/2本の選択ボタン（両手アイコンで視覚化）。AIのコール数字も実際の本数もまだ見えない、完全に手探りでタップする。**1ラウンド中は最初の1タップのみ受付、以降の連打・誤タップは無視する**。
3. **結果表示**：「AIのコールは○だった」を明示 → あなたの本数＋AIの本数＝合計 → 的中/不一致の判定バッジ → 腕の増減演出。

腕1本の場合：タップ入力画面の選択肢が0/1本のみになる（5-4参照）。

### 5-3. 人間がオフェンス（＝AIはディフェンス）の回

1. **コール選択（あなたの番）**：topbarに両者の残り腕、「合計を予想してタップ」、0〜4の選択ボタン（達成可能な上限までのみ有効）。自分でタップして能動的に選択する。
2. **せーのカウントダウン**：AIオフェンス時と同じ演出。
3. **タップ入力（あなたの攻撃）**：0/1/2本の選択ボタン。AIの実際の本数は見えない、自分のコールが当たるように賭ける。**1ラウンド中は最初の1タップのみ受付、以降の連打・誤タップは無視する**。
4. **結果表示**：あなたの本数＋AIの本数＝合計 → 的中/不一致の判定バッジ → 腕の増減演出。

腕1本の場合：コール選択の選択肢上限が下がり、タップ入力の選択肢も0/1本のみになる（5-4参照）。

### 5-4. 共通：腕が1本になったときの差分

- **コール選択（腕1本）**：自分の最大本数＋相手の最大本数＝コールの上限。上限を超える数字は選択不可（薄表示）。
- **タップ入力（腕1本）**：手のアイコンは1個だけ表示。選択肢は0/1本のみ（2本の選択肢自体が存在しない）。

### 5-5. 試合終了

**⑥ 勝敗画面**：勝敗表示、連勝カウント（🔥Nれんしょう中、アプリセッション中の一時カウント）、次の先行者表示（勝者が次コール担当）、「もういちど」「タイトルへ」ボタン。「もういちど」で新しい試合を開始する際は、両者の腕を2本にリセットする（連勝カウント・humanHistoryはリセットしない）。

### 5-6. 中断時の挙動

タイマー作動中（カウントダウン・0.9秒の入力受付中）にブラウザがバックグラウンドに回った場合（タブ切り替え・他アプリ切り替え・画面ロックなど）、**その時点で試合を中断し、復帰時はタイトル画面に戻す**。進行中のラウンド・試合の状態は破棄する（連勝カウント・humanHistoryなどのセッション状態は保持、7章参照）。

## 6. UI表現の指針

- 本数選択・結果表示は「手」アイコンで視覚化する。**表示する手の個数＝そのプレイヤーの残り腕本数**
  - 腕2本 → 手2個：0本=✊✊／1本=✊👍／2本=👍👍
  - 腕1本 → 手1個：0本=✊／1本=👍
- 世界観はシンプルな手・ジェスチャー系。マスコットキャラは作り込まない
- テンポ：カウントダウン各0.5秒×3＋せーの、入力受付0.9秒（合計約3秒）。実際に子供と遊んで駆け引きが成立することを確認済みのため、この初期値のまま採用（追加調整なし）
- 音声なし・文字最小限でも成立するデザインを徹底する（レストランでの利用を想定）。バイブレーション等の触覚フィードバックは**MVPでは入れない**（見送り）
- 結果バッジ（的中○／不一致✕）は記号自体の形状が異なるため色のみに依存しない設計になっている。**現状のままで問題なしと確認済み**、追加のアクセシビリティ対応は不要

## 7. セッション状態・戦績機能

連勝カウント・`humanHistory`（AIの学習データ）はいずれも**アプリセッション単位**で保持する（ブラウザタブを開いている間ずっと引き継がれる。試合が変わっても明示的にリセットしない）。ページの再読み込み・タブを閉じる操作でクリアされる。永続化（保存処理）は行わない。10戦中何勝といった永続戦績はMVP後の拡張へ。

## 9. AWSインフラ構成

バックエンド不要（認証なし・DB無し・AIロジックは全てクライアントサイドJS）のため、S3 + CloudFrontによる静的サイトホスティング構成とする。

| 項目 | 内容 |
|---|---|
| ホスティング | S3（静的ファイル配置、ブロックパブリックアクセスON） + CloudFront（CDN配信、HTTPS終端） |
| S3アクセス制御 | CloudFrontからのみ **OAC（Origin Access Control）** 経由でアクセス許可。S3への直接アクセスは不可 |
| 独自ドメイン | **使わない**。CloudFrontのデフォルトドメイン（`*.cloudfront.net`）で運用する（Route53・ACMは不要） |
| CI/CD | GitHub Actions → **OIDC federation**でIAM Roleを引き受け（長期アクセスキーは持たない） → S3への同期 + CloudFrontキャッシュ無効化 |
| 想定コスト | 独自ドメインなしのため**実質$0/月**（S3ストレージ・リクエストはごく僅か、CloudFrontはデータ転送1TB/月・リクエスト1,000万件/月の無料枠内に収まる想定） |
